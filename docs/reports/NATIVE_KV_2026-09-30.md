# Native engine: 16-bit KV cache and flash attention (2026-09-30)

Branch `perf/max-kv`. The scope is the attention and KV paths of
`babble/_native/engine.cpp`, plus the snapshot sizing in
`babble/nativeserve.py`. The GEMM and weight code is untouched.

Model: `hf-booper-longctx-v1`. Box: i7-4790, 4 engine threads.

Live prompts now carry up to 1536 tokens of history. At that length, the fp32
KV costs 43 KB per token per decode step. That is about as much bandwidth as
the weights.

## What changed

**KV storage: `BABBLE_NATIVE_KV=q16|fp16|fp32`, default `q16`.**

- **`q16`:**
  - K is stored as int16, with one fp32 scale per (position, head): max|k| / 32767.
  - V is stored as IEEE fp16 (F16C).
  - The scale multiplies the 16 scores of a K block after the dot product.
  - Cost: 260 B per position-head, against 512 B for fp32.
- **`fp16`:** K and V are both stored as IEEE half. It is kept for comparison only (see the parity table below).
- **`fp32`:** the previous cache, unchanged in precision.
- The storage type is a policy (`KVF32` / `KVF16` / `KVQ16`) over raw byte regions.
  - It applies to the prompt region, the per-stream regions, and the prefix snapshots.
  - A snapshot is now a `uint8` tensor of `eng_kv_bytes(P)` bytes, so `PrefixKVCache` byte accounting is exact.
  - A q16 snapshot is 21.8 KB per prompt token, against 43 KB, so the same cache MB holds 1.97x as many tokens.
- ABI 4: `eng_kv_bytes`, `eng_set_kv_type` and `eng_kv_type` replace `eng_kv_floats`.

**Decode attention (flash-decoding split-K).**

- Work units are (head, 256-position chunk of the shared prompt, row tile). Every stream's query scores the chunk while it is hot, so the prompt K/V is read once per step for all streams.
- The work is spread over all threads through a dynamic atomic queue. Before, there was one item per head: 14 heads over 4 threads, with 4/3.5 imbalance.
- The generated tail of each stream is its own unit, and does the RoPE plus the cache append.
- A merge pass combines the per-chunk (max, sum, out) partials.
- The kernels read fp16/int16 directly (`vcvtph2ps` / `vpmovsxwd`), with no staging copy.
- In a multi-thread microbench, decode attention runs at about 20.5-21 GB/s. That is the DRAM roof of this box.
- Software prefetch of the next block (T0/T1, 1-2 blocks ahead) did not help, because the hardware prefetcher already keeps up.

**Prefill attention (flash, tiled).**

- Work units are (48-query block, head), handed out longest first.
- Each 64-position K/V block is converted to fp32 once, and then used by all 8 six-row tiles of the unit.
- Softmax is online (running max and sum). Scores live in the log2 domain, with a cheaper `2^x`: a degree-6 fit, relative error 1e-7.
- Tiles on the causal diagonal only compute the keys they need.
- Throughput is 70-75 GFLOP/s per thread, against 65 before the exp2 change. The kernel peak is 107 GFLOP/s with the data in L1.

| decode | 0.0080 / 1.0 / -5.4e-5 | 0.0089 / 1.0 / -7.6e-5 | 0.0078 / 1.0 / -7.4e-5 |
| prefix | 0.0080 / 1.0 / -5.4e-5 | 0.0085 / 1.0 / -7.7e-5 | 0.0078 / 1.0 / -7.4e-5 |

Each cell is max|dlogit| / top1 / dNLL per token.

**Long-context parity** (`bench/extreme/longctx_parity.py`):

- 2048 tokens of repo docs, through longctx-v1, against transformers fp32 run live.
- Rows: full prefill; 1500-token prefill + 548 decode steps; a 1024-token snapshot restored + 1024 prefilled.

| KV | max\|dlogit\| (all three paths) | top1 | dNLL |
|---|---|---|---|
| fp32 | 3.9e-5 – 4.8e-5 | 1.0 | 0 – 2e-7 |
| **q16** | 4.0e-3 – 4.3e-3 | 1.0 | +5e-6 |
| fp16 | 1.25 (0.42 at positions >= 1536) | 0.998 | +6.0e-4 |

- **Why q16 rather than plain fp16.** Plain fp16 passes the gate on paper (top1 >= 0.995, |dNLL| < 0.002), but it moves some logits by more than 1.
  - The positions affected are 256-330 and 920.
  - An fp32-path emulation splits the error by source:

    | rounding emulated | max\|dlogit\| |
    |---|---|
    | K fp16 alone | 1.22 |
    | V fp16 alone | 0.0044 |
    | K int16 with per-position scale | 7.7e-4 |
    | K int8 | 3.9 |
    | V int8 | 3.1 |

  - So K needs the finer grid, which int16 with a scale gives at the same 2 bytes per element.
- `q16` is the default. `fp16` is selectable but not recommended.
- `pytest`: 902 passed, 1 skipped on the track branch. New tests cover:
  - the KV type, the env var and the snapshot sizes
  - agreement of fp16/q16 across paths
  - a 700-token tiny model, exercising multi-tile prefill and 3-chunk split-K decode against transformers to 1e-4 in fp32
  - 50 streams, which is two decode row tiles

## Speed

Protocol:

- `/tmp/maxperf/kv/bench_kv.py` drives `NativeEngine.generate` directly.
- Workload: best-of-4, 64 new tokens, live sampling (T 0.5, top-k 40, top-p 0.9, rep 1.15, no-repeat-4), EOS ignored.
- Decode-1 is greedy, 128 tokens after a 27-token prompt.
- Metrics: steady = 4·63/(last − first token); TTFT is from engine entry.
- Main's engine and this branch ran in separate processes, interleaved, under `flock /tmp/babble-bench.lock`.
- 5 rounds × 3 reps, so each cell is the median of 15.

## Risks and notes

- **q16 is not bit-identical to fp32.** It is within ~4e-3 logits at 2048 tokens on the gate prompts. An independent review on 38,880 real-text positions found that on some prompts the rounding flips a near-tie top-1 MoE route; a few per cent of later positions then move by up to ~4 logits (30 argmax flips in total, top1 0.9992). This is above the 0.995 gate and small next to T=0.5 sampling noise, so q16 stays the default; `BABBLE_NATIVE_KV=fp32` is the exact option. The fp32-exactness tests now pin `kv="fp32"`; the 16-bit modes have their own tolerance tests.
- **Snapshots are typed by KV mode.** The mode is fixed per engine, and the prefix cache lives in that engine's generator, so mixed snapshots cannot occur.
- **K int16 clipping cannot happen**, because the scale is the per-position max.
- **Rollback:** set `BABBLE_NATIVE_KV=fp32` and restart. No rebuild is needed; it is the same library.
