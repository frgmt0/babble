# Moving booper onto depper: cutover and rollback runbook

This runbook moves the live booper bot on jason's desktop from the hand-rolled
setup (`~/babble-live` clone + systemd `--user` unit `babble-bot`) to a
[depper](https://github.com/frgmt0/depper) deployment (`depper-babble.service`)
described by `depper.toml` at the repo root.

**Status: not cut over.** Until every step below has been done, the hand-rolled
setup in `CLAUDE.md` is still what runs booper and is still authoritative.
Nothing in this repo changes the live box by itself.

Everything here assumes the box and accounts as they were inspected on
2026-10-17 (read-only): host alias `desktop`, user `jason`, Arch Linux with
systemd 261, linger on, `uv` 0.12.15 at `/home/jason/.local/bin/uv`, one
btrfs filesystem for all of `/home`, `babble-bot` and `babble-boopit` active,
**`babble-update.timer` not installed**, nothing under `~/.local/share/depper`.
Re-check anything that may have changed since (step 1 does).

## What changes, and the decisions behind it

| | before | after |
| --- | --- | --- |
| code | `~/babble-live` (git clone of `main`) | `~/.local/share/depper/babble/releases/<id>` (git archive of `main`, last 3 kept) |
| venv | `~/babble-live/.venv` | `<release>/.venv`, built per release by `[deploy].setup` |
| unit | `babble-bot.service` (hand-written) | `depper-babble.service` (generated by depper) |
| non-secret config | `~/babble-live/.env` | `[env]` in `depper.toml` (versioned) |
| secrets | `~/babble-live/.env` | `.env.prod` on the machine you deploy from, gitignored; depper writes it to `~/.local/share/depper/babble/.depper/environment` (mode 600) |
| state | `~/babble-live/{data,checkpoints,...}` | `~/.local/share/babble/{data,checkpoints,...}` |
| code updates | `deploy/update-live.sh` (timer, if installed) | `depper deploy` from an up-to-date `main` |

### Where state goes, and why it moves

depper prunes release directories, so nothing the bot writes may live inside
one. The state moves to **`/home/jason/.local/share/babble/`**, next to the
other services on this host (`~/.local/share/skeebert`, `~/.local/share/tendies`),
instead of staying inside `~/babble-live`:

- `~/babble-live` is a git checkout that this runbook eventually retires. If
  the state stayed there, the "old" clone could never be deleted and would
  keep a second copy of the code next to the real one.
- The move is a **copy, not a rename** (`cp -a --reflink=auto`; on this
  btrfs `/home` it is near-instant and shares blocks). The originals stay
  untouched as the pre-cutover snapshot, which is what makes rollback simple.
- The bot is stopped before the copy, so the copied files are a consistent
  snapshot, and every file is verified with sha256 before the new unit starts.

| state | env var that controls it | new location | notes |
| --- | --- | --- | --- |
| consented corpus, consent records, exchanges, publish state, **hash salt** (`data/.salt`) | `BABBLE_DATA_DIR` | `/home/jason/.local/share/babble/data` | the salt path is always `$BABBLE_DATA_DIR/.salt`; `BABBLE_HASH_SALT` is not set on this box |
| `latest.pt`, `pretrained.pt`, `tokenizer.json` | `BABBLE_CHECKPOINT_DIR` | `/home/jason/.local/share/babble/checkpoints` | |
| `babble.log`, `babble.jsonl` (+ rotations) | `BABBLE_LOG_DIR` | `/home/jason/.local/share/babble/logs` | |
| dataset export staging | `BABBLE_EXPORT_DIR` | `/home/jason/.local/share/babble/export` | |
| promoted HF snapshots, spec n-gram tables | **no env var for the directory.** The code reads only the two files below | `/home/jason/.local/share/babble/artifacts` | `BABBLE_HF_MODEL_DIR` (served model dir) and `BABBLE_NATIVE_SPEC_TABLE` point into it |
| checkpoint/env backups | **no env var**: a human convention, never read by code | `/home/jason/.local/share/babble/backups` | convention: `backups/<reason>-<date>/checkpoints/` |
| compiled native engine | `BABBLE_NATIVE_CACHE` (default `~/.cache/babble/native`) | unchanged | already outside both trees |
| HuggingFace login used by auto-publish | `HF_TOKEN` is **not** in the live `.env`; huggingface_hub reads `~/.cache/huggingface/token` (present) | unchanged | |

Every directory babble's code resolves on its own is covered by the four
`BABBLE_*_DIR` variables (`Settings.from_env` in `babble/config.py`); there is
no state path that cannot be overridden. One thing does depend on the code
location: `babble summary`'s `code` line runs `git rev-parse` in the code
directory, and a release directory has no `.git`, so after cutover it prints
`unknown (not a git checkout)`. Use `depper status` (it shows the deployed
commit) instead. Nothing else is affected.

### `[env]` vs `.env.prod`

`[env]` in `depper.toml` holds everything that is not a secret **and** whose
value is known from the repo:

- the four state dirs above;
- the four invariants from `CLAUDE.md`: `BABBLE_SERVE_LAYOUT=pair`,
  `BABBLE_POST_LAYOUT=pair`, `BABBLE_TRAIN_TRIGGER_ROWS=0`,
  `BABBLE_POST_TRIGGER_PAIRS=0`. They are versioned now, so a lost `.env`
  can no longer silently re-enable auto-training or flip the layout;
- `BABBLE_HF_MODEL_DIR` and `BABBLE_NATIVE_SPEC_TABLE`, which must change
  anyway because `artifacts/` moves. Their values come from
  `docs/reports/LONGCTX_V2_PROMOTE_2026-10-15.md` and
  `docs/reports/MAXPERF_PROMOTE_2026-09-30.md`; step 1 checks them against
  the live `.env`.

`.env.prod` holds the two secrets (`BABBLE_DISCORD_TOKEN`,
`BABBLE_LOG_WEBHOOK_URL`) **and** the remaining serving knobs from the live
`.env`, copied verbatim: `BABBLE_SERVE_BACKEND`, `BABBLE_HF_RUNTIME`,
`BABBLE_NATIVE_SPEC`, `BABBLE_NO_REPEAT_NGRAM_SIZE`,
`BABBLE_CONVERSATION_CONTEXT`, `BABBLE_CONVERSATION_MAX_TURNS`,
`BABBLE_CONVERSATION_MAX_TOKENS`, `BABBLE_CONVERSATION_MAX_CHARS`,
`BABBLE_MAX_NEW_TOKENS`. Those are not secrets, but their current values
were not read when this was written (only key names were), so they are
carried over exactly instead of being re-typed from old reports. Moving them
into `[env]` afterwards is a safe follow-up: read the values, add them to
`[env]`, delete them from `.env.prod`, run `depper secrets diff` (it must
show no changed values), deploy.

**dotenv values override `[env]`.** A key that is in both places takes the
`.env.prod` value. That is why step 3 strips every `[env]` key out of the
copy and then checks that the overlap is empty: a stale
`BABBLE_HF_MODEL_DIR=/home/jason/babble-live/...` left in `.env.prod`
would silently point the new bot at the old tree.

### Health check

`[health].command` runs `deploy/depper-healthcheck.sh depper-babble.service`
on the host. It passes only when the unit is active **and** the newest
`bot.ready` in `$BABBLE_LOG_DIR/babble.jsonl` (or `.jsonl.1` after a rotation)
is stamped at or after the unit's own `ExecMainStartTimestamp`. A `bot.ready`
written by the old `babble-bot` process, or by the previous release, is older
than the new process and cannot pass it. `start_period = 180` seconds covers
model load, a possible first-start native engine compile, and the Discord
login (update-live.sh allowed 90). depper also fails the deploy early if the
unit restarts or enters the failed state.

The script was exercised read-only against the live units on 2026-10-17:
against `babble-bot` with `~/babble-live/logs` it passed (`bot.ready at
2026-10-16T04:13:15+00:00`, process started `@1792123990`); against the
not-yet-existing `depper-babble.service` it failed (`inactive`); against
`babble-bot` with boopit's log dir it failed (newest `bot.ready` predates the
process start).

### Dependencies

`[deploy].setup` runs, in the new release directory:

1. a guard that **refuses the deploy before anything is activated** unless
   `data/.salt`, `data/consent.json`, `checkpoints/latest.pt`,
   `checkpoints/tokenizer.json`, the served model's `model-int8.safetensors`
   and `tokenizer.json`, and the spec table all exist at the new paths. A
   deploy started before the data move would otherwise run the bot on an
   empty data dir, where it would mint a **new** hash salt;
2. `uv sync --frozen --no-dev --python 3.12`: the locked base dependencies,
   CPU-only torch (the `pytorch-cpu` index in `pyproject.toml`), no pytest;
3. `uv pip install` of the `hf` extra pinned to the exact versions in the old
   live venv (`transformers==5.16.1`, `safetensors==0.8.0`,
   `tokenizers==0.23.1`, and their non-locked dependencies). The native and
   lean runtimes the live bot uses import `safetensors` and `tokenizers`.
   `uv.lock` does not contain the `hf` extra (its `provides-extras` is
   `["dev", "pretrain"]` and `uv lock --check` reports it out of date), so
   `uv sync --extra hf --frozen` cannot install it. Regenerating `uv.lock`
   (`uv lock`, in its own PR) and replacing steps 2 and 3 with
   `uv sync --frozen --no-dev --extra hf --python 3.12` is the cleaner
   long-term setup.

Version differences between the new venv and the old one, all within the
locked ranges: `numpy` is pinned to the old `2.5.2`; `huggingface-hub` comes
from the lock (`1.27.0`, old venv had `1.28.0`), and a few small transitive
packages (`filelock`, `fsspec`, `idna`, `networkx`, `pygments`) also take the
lock's versions. The old venv was not built from the lock either.

### boopit

`babble-boopit.service` runs `~/babble-live/.venv/bin/babble bot` with
`WorkingDirectory=~/babble-boopit` and its own `.env`, which sets all four
`BABBLE_*_DIR` variables to `~/babble-boopit/...`. It shares **code and venv**
with `~/babble-live` but **no state** with booper.

- **At cutover it is left alone.** Moving booper's state out of
  `~/babble-live` does not touch anything boopit reads, `~/babble-live/.venv`
  stays where it is, and boopit is never stopped or restarted.
- **Consequence:** boopit keeps running the code at `~/babble-live`'s commit
  (`ea17654` on 2026-10-17). Nothing updates that clone after cutover.
- **`~/babble-live` cannot be deleted until boopit is repointed** (section 9).
- Observed on 2026-10-17, outside the scope of this runbook: boopit's
  `~/babble-boopit/checkpoints` is empty and its newest `bot.ready` is
  2026-10-03. Check whether boopit is still wanted before investing in it.

## 0. Before you start

- [ ] The PR adding `depper.toml`, `deploy/depper-healthcheck.sh` and this
      runbook is **merged to `main`**. `source = "git"` deploys the committed
      `HEAD`, so the health script must be committed to be on the host.
- [ ] You are the only one touching the live box (CLAUDE.md: the live box is
      single-writer). No other session is deploying, promoting or editing `.env`.
- [ ] `depper --version` works on the machine you deploy from (the Mac:
      `~/.local/bin/depper`), and `ssh desktop true` works without a prompt.
- [ ] You have a few minutes of booper downtime: from step 4 (stop) to the end
      of step 6 (deploy healthy). The first deploy builds a venv; most wheels
      come from the host's uv cache.

## 5. Copy the state and verify it [host]

The bot is stopped, so `data/` is quiescent.

```bash
# manifest of every file whose loss or change would hurt, relative paths
(cd $OLD && find data checkpoints artifacts -type f -print0 | sort -z | xargs -0 sha256sum) > $BK/sha256-before.txt
wc -l $BK/sha256-before.txt

if [ -e "$NEW" ]; then
  echo "STOP: $NEW already exists"
else
  mkdir -p "$NEW" && for d in data checkpoints artifacts backups logs export; do
    cp -a --reflink=auto "$OLD/$d" "$NEW/" || echo "COPY FAILED: $d"
  done
fi

# every file, byte for byte
(cd $NEW && sha256sum --quiet -c $BK/sha256-before.txt) && echo "ALL FILES MATCH"
# the ones that matter most, side by side (do not paste the salt's hash into reports or PRs)
sha256sum $OLD/data/.salt $NEW/data/.salt
sha256sum $OLD/checkpoints/{latest.pt,pretrained.pt,tokenizer.json} $NEW/checkpoints/{latest.pt,pretrained.pt,tokenizer.json}
# permissions survived (.salt, consent.json and exchanges.json are 600)
stat -c '%a %n' $NEW/data/.salt $NEW/data/consent.json $NEW/data/exchanges.json
ls $NEW/artifacts/hf-booper-longctx-v2/model-int8.safetensors $NEW/artifacts/spec-ngram-longctx-v1.pt
```

`ALL FILES MATCH`, identical pairs, and `600` on the three data files are
required. Anything else: stop and go to **Rollback A**.

## 6. First deploy [mac]

```bash
depper deploy
```

What happens: lock, upload of the `main` archive, setup (state guard,
`uv sync`, the `hf` pins), install and start `depper-babble.service`, then
up to 180 s of health checks. Success ends with the release id and a health
line like `bot.ready at 2026-..T..+00:00; depper-babble.service pid N started @...`.

If the deploy fails, depper removes the unit and the release again (first
deploy, nothing to restore). booper is then down: either fix the cause and
`depper deploy` again, or go to **Rollback A**.

## 8. Rollback

### Rollback A: back to `babble-bot` (cutover abandoned)

Use this at any point after step 4, including after a successful cutover.
`~/babble-live` was never modified, except that the bot stopped writing to it.

```bash
# [host]
# 1. stop the depper unit and keep it from starting at boot
systemctl --user disable --now depper-babble.service 2>/dev/null || true
systemctl --user show -p MainPID --value depper-babble.service      # 0 (or unit not found)

# 2. bring back anything the new bot wrote. data/ must be mirrored exactly:
#    consent changes and `!babble forget` purges made after cutover live only
#    in $NEW/data, and must not be undone by going back.
#    Skip 2a-2c if step 5 never created $NEW/data.
#    2a. the salt must be the same file. If cmp reports ANY difference, stop
#        here and investigate; do not copy anything.
cmp $OLD/data/.salt $NEW/data/.salt && echo "salt identical"
#    2b. mirror data back, keep the logs
rsync -a --delete $NEW/data/ $OLD/data/
rsync -a $NEW/logs/ $OLD/logs/
#    2c. checkpoints/ and artifacts/: only if something was promoted or
#        trained while on depper. Then copy those files back the same way,
#        and set the matching BABBLE_HF_MODEL_DIR / BABBLE_SERVE_LAYOUT in
#        $OLD/.env.

# 3. the old unit and .env are unchanged; start it
cmp $BK/env.before $OLD/.env && echo ".env unchanged"
cmp $BK/babble-bot.service ~/.config/systemd/user/babble-bot.service && echo "unit unchanged"
systemctl --user daemon-reload
systemctl --user enable --now babble-bot.service

# 4. wait for a bot.ready from THIS process -- do not walk away before it.
#    The log timestamp (UTC) must be later than the start time (local time).
systemctl --user show -p ExecMainStartTimestamp --value babble-bot.service
grep 'bot.ready' $OLD/logs/babble.log | tail -n 1     # repeat until it is newer
```

Then a real ping, `~/babble-live/.venv/bin/babble logs -n 20`, and
`sha256sum $OLD/data/.salt` against the value from step 5.

The depper deployment stays on disk (`depper status` shows it inactive). To
remove it later: `systemctl --user disable --now depper-babble.service`,
`rm ~/.config/systemd/user/depper-babble.service`,
`systemctl --user daemon-reload`, then delete `~/.local/share/depper/babble`.
Delete `$NEW` only after confirming step 2 copied everything back.

### Rollback B: a bad code release, while on depper

```bash
# [mac]
depper rollback          # previous release, with the environment it was deployed with
depper status
```

State is outside the releases, so data is untouched. depper waits for the
health check again and undoes the rollback if it fails.

## 9. After cutover: operating and retiring the old setup

**Deploying a change:** land it on `main`, then from a clean, up-to-date
`main`: `depper deploy`. depper does not check for an in-flight training run
(update-live.sh did); check `pgrep -af 'babble (train|post-train)'` on the
host first.

**Promoting a model:** copy it into `$NEW/artifacts/` (or the checkpoint pair
into `$NEW/checkpoints/`), backed up first under
`$NEW/backups/<reason>-<date>/checkpoints/`. Change `BABBLE_HF_MODEL_DIR` (and
`BABBLE_SERVE_LAYOUT` if needed) in `[env]` on `main`, then `depper deploy`.
`depper secrets push` also rewrites the environment from `[env]` +
`.env.prod` and restarts with a health check, without a new release, if only
the environment changed.

**Retiring the old setup**, once booper has run on depper long enough that you
will not use Rollback A (each item is independent; do them in this order):

1. Remove the old unit: `rm ~/.config/systemd/user/babble-bot.service && systemctl --user daemon-reload`
   (a copy is in `$BK/`).
2. **Remove stale copies of consented data.** `$OLD/data` and `$OLD/logs` are
   now a frozen copy of people's messages that `!babble forget` no longer
   reaches. After the last date you would use Rollback A:
   `rm -r $OLD/data $OLD/logs`. Do not delete `$NEW/data`.
3. Repoint boopit, because it still runs `~/babble-live/.venv`:

   ```bash
   # [host]
   mkdir -p ~/.config/systemd/user/babble-boopit.service.d
   printf '[Service]\nExecStart=\nExecStart=%%h/.local/share/depper/babble/current/.venv/bin/babble bot\n' \
     > ~/.config/systemd/user/babble-boopit.service.d/depper.conf
   systemctl --user daemon-reload
   systemctl --user restart babble-boopit.service
   BABBLE_LOG_DIR=~/babble-boopit/logs ~/.local/share/depper/babble/current/.venv/bin/babble logs -n 20   # wait for bot.ready
   ```

   depper restarts only `depper-babble`, so after each `depper deploy`, also
   `systemctl --user restart babble-boopit.service`. Otherwise boopit keeps
   running an older release, whose directory is deleted once it falls out of
   `keep_releases = 3`.
4. Only after 1-3 and with `$NEW` verified: delete `~/babble-live`
   (`$NEW/backups` already has every backup from it).
5. In a follow-up PR, update `CLAUDE.md` ("Live deployments", "Deploying a
   change", "Quick reference") and the README's "Running it for real" and
   "Keeping the live install current" sections to the depper setup.
